# 2.1 算法效率的度量

算法效率的高低，体现在运行该算法所需要耗费资源的多少。对计算机而言，最重要的资源是**时间**和**空间**，因此算法效率分为**时间效率**与**空间效率**。

## 2.1.1 从“跑一遍”到“算出来”

最朴素的做法是把程序跑一遍，用秒表计时。这种**事后统计**方法有致命缺陷：

- 依赖机器性能、编译器优化、操作系统负载，换台电脑结果就不同；
- 必须先把程序写完、数据造好，无法在设计阶段比较；
- 无法解释“为什么 $n$ 翻倍后时间变成四倍”。

因此我们采用**事前分析**：在算法运行之前，用数学方法估计它的资源消耗随问题规模的增长趋势。

## 2.1.2 复杂度的形式化描述

设 $N$ 表示问题的**规模**，$I$ 表示算法的**输入实例**，$A$ 表示**算法本身**，$C$ 表示复杂性，则

$$C = F(N, I, A)$$

把时间与空间分开，记作

$$T = T(N, I), \qquad S = S(N, I)$$

这里 $N$ 与 $I$ 之所以并列，是因为**同样规模的不同输入，执行时间可能相差巨大**：在长度为 $n$ 的数组中查找一个元素，待查元素在第一个位置和不在数组中，比较次数分别是 $1$ 和 $n$。

::: info 为什么可以忽略算法 $A$？
上式本应写成 $T(N,I,A)$。但当我们比较的是“同一个问题的不同算法”时，$A$ 已经被具体算法固定下来，于是 $T$ 只随 $N$ 和 $I$ 变化。若把 $A$ 也当作变量，就变成“算法之间的比较”，那正是我们后续要讨论的内容。
:::

## 2.1.3 元运算模型

为了摆脱具体机器的干扰，我们在一台“抽象的计算机”上讨论运行时间。设这台机器提供 $k$ 种**元运算** $O_1,O_2,\dots,O_k$，执行一次分别耗时 $t_1,t_2,\dots,t_k$，且这些 $t_i$ 是与 $N,I$ 无关的常数。

对给定算法，统计执行过程中元运算 $O_i$ 被调用的次数 $e_i = e_i(N,I)$，则

$$T(N,I) = \sum_{i=1}^{k} t_i\, e_i(N,I)$$

进一步，若把每种元运算的常数时间都视为 $1$（即只关心“执行了多少条基本指令”），就得到

$$T(N,I) = \sum_{i=1}^{k} e_i(N,I)$$

这就是“**基本操作计数**”模型。

::: tip 为什么要抽象？
1. **可移植**：结论不依赖具体 CPU 的主频与指令集；
2. **可比较**：不同算法可以放在同一把尺子下；
3. **抓住主要矛盾**：当 $N$ 很大时，常数因子和低阶项可以忽略，真正决定胜负的是**增长率**。
:::

## 2.1.4 最好、最坏与平均情况

我们不可能对规模为 $N$ 的每一种合法输入 $I$ 都去统计 $e_i(N,I)$。通常取三种代表：

**最坏情况**（上界，最常用）：

$$T_{\max}(N) = \max_{I \in D_N} T(N,I) = \max_{I \in D_N} \sum_{i=1}^{k} t_i e_i(N,I)$$

**最好情况**（下界）：

$$T_{\min}(N) = \min_{I \in D_N} T(N,I)$$

**平均情况**（期望）：

$$T_{\text{avg}}(N) = \sum_{I \in D_N} P(I)\, T(N,I)$$

其中 $D_N$ 是规模为 $N$ 的全部合法输入集合，$P(I)$ 是输入 $I$ 出现的概率。

| 情况 | 关注点 | 用途 |
| :--- | :--- | :--- |
| 最坏 | 保证任何输入都不超过的上限 | 实时系统、考试分析、算法下界 |
| 最好 | 最理想输入下的下限 | 分析算法是否“自适应” |
| 平均 | 随机输入下的期望表现 | 评估实际使用体验 |

::: warning 平均情况并不好算
平均分析必须知道**输入的概率分布**。若假设所有输入等概率，而实际数据并非均匀分布，结论就会失真。因此工程与考试中，**最坏情况**是最常用的度量；只有在分布明确时（如随机化快速排序），平均分析才有意义。
:::

### 例：顺序查找的三种情况

在长度为 $n$ 的数组中查找 $x$：

- **最好**：第一个元素就是 $x$，比较 $1$ 次，$O(1)$；
- **最坏**：$x$ 不在数组中，比较 $n$ 次，$O(n)$；
- **平均**：若 $x$ 以等概率出现在任一位置或不存在，则平均比较次数约为 $(n+1)/2$，仍是 $O(n)$。

### 关于摊销效率

有些数据结构（如动态数组、并查集）的单次操作可能很贵，但**连续 $n$ 次操作的总代价**可以被摊薄。例如动态数组扩容：每次容量翻倍，插入 $n$ 个元素的总复制次数不超过 $2n$，因此单次插入的**摊销代价**是 $O(1)$，尽管最坏情况下某一次插入是 $O(n)$。

> 摊销分析不是“平均分析”：它不依赖概率假设，而是对**操作序列的总代价**做确定性核算。

## 2.1.5 空间复杂度

空间复杂度 $S(n)$ 衡量算法运行所需的**辅助空间**随规模的增长。注意区分：

- **输入本身占用的空间**通常不计入；
- **辅助数组、递归栈、临时变量**才计入；
- 若辅助空间是常数，称算法**原地工作**，$S(n)=O(1)$。

| 算法 | 辅助空间 | 说明 |
| :--- | :--- | :--- |
| 选择排序 | $O(1)$ | 只用几个临时变量 |
| 归并排序 | $O(n)$ | 合并需要辅助数组 |
| 快速排序 | $O(\log n)$ | 递归栈平均深度 |
| 动态规划（矩阵连乘） | $O(n^2)$ | 二维表格 |
| 回溯法 | $O(n)$ | 解向量与递归栈 |

## 2.1.6 效率比较的正确姿势

对同一问题的不同算法，我们最终把 $T(N,I)$ 抽象为**问题规模 $N$ 的函数**，再比较它们的**增长阶**：

- 若 $T_1(n) = 3n^2 + 100n$，$T_2(n) = 0.01n^3$，当 $n$ 足够大时，$T_1$ 一定优于 $T_2$；
- 常数因子只在“小规模”或“同阶算法”之间才有意义；
- 比较时通常忽略系数与低阶项，这正是下一节**渐近记号**要解决的问题。

::: tip 一个常被忽略的事实
$O(n\log n)$ 的归并排序在小数组上往往跑不过 $O(n^2)$ 的插入排序，因为归并排序有递归与辅助数组的常数开销。工程实现中，标准库通常会在小数组上切换为插入排序（如 Java 的 `Arrays.sort`、C++ 的 `std::sort`）。
:::
